# Phone construction and delivery evidence

Chapter 6 constructs the narrow Telegram API wrapper, complete durable admission helper, poller lease, atomic cursor/work transaction, private numeric-operator/session routing, owned-loop bridge and outbound delivery state. Its local bot replays unordered intake and accepts a report before losing the reply. The chapter distinguishes that deterministic fixture from a live API request and an actual handset observation. The cumulative checkpoint preserves the active opening skill, authenticated session context, model budget hook and no-purchase dispatcher. Ten runnable Python/output pairs demonstrate the mechanism.

A reproduced malformed message object previously raised uncaught AttributeError; transaction rollback worked, but the service's controlled retry catch did not cover the parser failure. The adapter now checks envelope/update/message/sender/chat object shapes and exact integer chat identity, raising sanitized errors. Both intake and delivery validate the numeric allowlist. Valid unsupported non-text updates remain ignored; malformed batches refuse without advancing the cursor.

Successful sendMessage responses now require a positive non-boolean integer message ID. The conditional SENDING -> SENT update and append-only assistant.channel.sent event share one transaction. The event retains work, channel, requested recipient and message ID, not raw response bodies or credentials. If local state changed before completion, the old response returns UNKNOWN and cannot append a stale success event. A failed receipt-event commit leaves SENDING as uncertain admission; no blind resend occurs.

The live-channel checkpoint was inspected for restart behavior before use. It now queries durable READY work instead of relying on newly returned poll IDs, drains prior pending reports, and attributes delivery state by each work ID. An offline test executes the actual live-channel entrypoint with a local bot, no new updates, one unfinished request and one earlier completed report; both resume correctly and a subsequent empty run claims no new success or delivery.

The local setup helper telegram_identity_v1.py uses a fresh one-time private-message challenge to discover a numeric ID for operator review. It never enrolls an account, creates work or confirms/discards upstream updates. It refuses multiple matching identities and bounds polling to three requests. Tests reject group/bot/boolean/mismatched/malformed identities and confirm exact challenge matching. Use a dedicated bot without another poller or unrelated backlog. This is not a general account-pairing platform.
