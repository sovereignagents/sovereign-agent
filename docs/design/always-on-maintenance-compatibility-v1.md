# Upgrade, rollback and unknown schema refusal

The Linux maintenance experiment now extends the earlier worker-kill/reboot proof. Frozen release cec0452 upgraded the same actual database inode from schema 22 to 24, preserving four completed work records. Both enabled user services started on the new executable. A pre-upgrade SQLite backup remains unchanged. A subsequent controlled account-recovery exercise restored state predating two supplier orders, fenced the old supplier client, imported both receipts, installed explicit physical observations, settled 2600 pence once and resumed actual main-service work. Old model usage remains marked incomplete. Evidence linux-maintenance-v1.json pins the actual release hashes and records the outputs.

Compatible-code switching cec0452 -> 313ac06 -> cec0452 kept schema 24, both order records, inventory and spending unchanged; actual service work completed after each switch. The experiment returns to the newer release. This is an isolated test of rollback between reviewed compatible releases. Matching schema numbers alone cannot certify behavioral or authority compatibility. The old schema-22 executable was refused by a read-only preflight because it did not know migrations 23 and 24. No database downgrade was attempted. Historical deployment code is not transplanted into current source.

A separate reproduction against 313ac06 added migration 999 to a scratch database. Database reopened it and permitted a preference write. The loader now checks for unknown migrations before journal-mode changes or migrations, closes the refused connection, and checks compatibility on explicit migrate calls. applied_versions treats only an absent ledger table as empty; malformed existing ledger columns raise instead of inviting initialization. Four new tests prove unchanged database/authority bytes, closed rejection connections, refusal before otherwise-pending known migrations, direct migration refusal and malformed-ledger refusal. Existing forward-migration and transactional-failure tests still pass.

The guard applies to opening/migrating a database with this code. It is not a fence for already-running older processes, and it cannot retrofit a guard into a previously released binary. Stop both workers before migration and perform the read-only compatibility preflight before using a historical executable. Restoring a backup is a separate operation: it changes authority, starts paused, and requires account reconciliation and fresh observations; code rollback does not imply restoring old business state.

The one-account supplier protocol is controlled teaching infrastructure. Its complete retained history and epoch check are explicit dependencies of recovery. The maintenance experiment stopped its temporary supplier process after proving service resumption; it does not claim a currently running supplier endpoint or live phone integration.
